# Clase 01 — Organización del curso

### 1️⃣ 📘 Identificación

- **Tema principal:** presentación del curso y de las formas de trabajo.
- **Subtemas y actividades:** expectativas profesionales; análisis previo a la solución; protocolo “Zero Assumption”; dinámica de tareas, participación y entregas; presentación de herramientas de apoyo; introducción a ramas en Git; cuestionario inicial.
- **Propósito:** acordar hábitos de trabajo y presentar los métodos y herramientas que se usarán durante la materia.

### 2️⃣ 📝 Resumen explicativo

**Inicio y participación.** La sesión se planteó como introductoria. El profesor pidió participación activa, toma de notas y preguntas; también indicó que se reservaría tiempo al final de las clases para aclaraciones. La actividad inicial permitió que el grupo se presentara y comentara, de manera general, sus intereses en computación y sus motivos para elegir la carrera.

**Expectativas profesionales.** Se subrayaron la ética, disciplina, responsabilidad, compromiso, honestidad, juicio crítico y uso de métodos. El profesor relacionó estas actitudes con el trabajo cotidiano: no basta con saber programar si no se informa con honestidad cuánto tomará una tarea, si no se entiende lo que se entrega o si no se actúa responsablemente cuando algo falla. También recomendó cultivar autonomía, aprendizaje autodidacta, resiliencia, innovación y creatividad, y mantener apertura a áreas relacionadas con la computación.

**Analizar antes de proponer.** Antes de prometer una funcionalidad o comenzar a construir una solución, se debe comprender el sistema y el problema. El análisis parte de reunir datos, formular preguntas, revisar el contexto y anticipar qué consecuencias tendría un cambio. Aceptar una solicitud sin conocer la estructura o las restricciones puede producir soluciones improvisadas, aumentar el tiempo de trabajo y complicar la operación. Cuando una solución rápida sea necesaria, después se debe revisar y mejorar con más información.

**Protocolo “Zero Assumption”.** El profesor presentó una rutina para reducir errores por suposiciones:

1. Leer las instrucciones, identificar requisitos y comprobar el contexto.
2. Entender la lógica de lo que se está haciendo y por qué funciona o falla.
3. Corroborar la información y lo que se entendió antes de continuar.
4. Conservar evidencia verificable del trabajo, como registros, notas, enlaces o resultados de pruebas.
5. Validar el resultado. Si quedan dudas o la información no es confiable, regresar al primer paso y repetir el ciclo.

La intuición sin datos se trató como una sospecha, no como una conclusión. La evidencia debe permitir comprobar el trabajo realizado, no solo que existe un archivo.

**Dinámica, materiales y herramientas.** Se anunciaron ejercicios durante la clase, tareas, exámenes y posibles trabajos adicionales. Se priorizarían ejercicios, tareas y exámenes; habría trabajo individual y en equipo. Para las actividades escritas se pidió llevar cuaderno, hojas y útiles, y entregar trabajos legibles y hechos a mano cuando así se indique. El uso de IA estaría permitido salvo que una actividad especifique otra fuente; cuando se requiera investigación externa, se pedirían referencias bibliográficas. El objetivo es entender el contenido y poder explicarlo, no depender de una herramienta.

Se presentaron GitHub, PlantUML, Confluence, Markdown y Visual Studio Code. El proyecto se documentaría en Confluence, mientras que Git/GitHub serviría para algunas entregas y para practicar el control de versiones. El profesor indicó que las actividades anunciadas podrían hacerse con opciones gratuitas.

**Ramas en Git.** Se usó una analogía de versiones paralelas para explicar que una rama parte de un estado común y puede recibir cambios propios. Los cambios hechos en una rama no aparecen automáticamente en otra. Las ramas permiten probar o desarrollar alternativas sin modificar de inmediato la rama principal; el versionamiento también puede usarse con archivos que no sean código fuente.

**Actividad y tareas.** Se asignó un cuestionario escrito para entregar en la siguiente clase. Incluye preguntas sobre conocimientos previos de la materia, análisis de sistemas, programación, algoritmos, sistemas distribuidos, experiencia laboral y autoevaluación de fortalezas y áreas por desarrollar. También se anunciaron dos tareas: un videotutorial sobre GitHub y una página en Confluence. Sus fechas y horas de entrega quedarían en la plataforma. Durante la sesión hubo un problema temporal al publicar las tareas; el profesor las revisó y confirmó su aparición. Se indicó que la evaluación completa se revisaría el viernes.

### 3️⃣ 🧩 Conceptos teóricos y técnicos relevantes

- **Análisis de sistemas:** comprender el problema, el contexto, los datos y las restricciones antes de proponer cambios.
- **Evidencia:** información que permite comprobar una actividad, como registros, enlaces, notas de prueba o resultados verificables.
- **Resiliencia:** capacidad de responder y recuperarse cuando una operación o sistema falla; se ilustró con la atención de incidentes.
- **Autonomía profesional:** capacidad de tomar decisiones informadas a partir del conocimiento y el análisis.
- **Control de versiones:** seguimiento de cambios en archivos para comparar estados y recuperar o revisar versiones anteriores.
- **Rama (branch):** línea de trabajo derivada de una rama base. Sus cambios no aparecen en otra rama hasta que se integren.
- **Zero Assumption:** ciclo de revisar, comprender, corroborar, evidenciar y validar, regresando al inicio si persisten dudas.

### 4️⃣ ⚠️ Problemas, errores o aclaraciones del profesor

- No se debía asumir que una tarea, instrucción o archivo faltaba sin verificar primero la plataforma y el contexto; si el material no aparece, hay que reportarlo y comprobarlo.
- Una captura del nombre de un archivo no prueba que su contenido esté completo; la evidencia debe permitir revisar el resultado.
- El uso de IA depende de lo que indique cada tarea. Si se exige investigación bibliográfica, deben usarse y citarse las fuentes requeridas.
- La explicación de ramas fue introductoria. El procedimiento concreto para crear ramas y registrar cambios quedó como práctica posterior.
- El profesor indicó que los criterios completos de evaluación se revisarían en otra sesión; no quedaron establecidos en esta transcripción.

### 5️⃣ 🧠 Conclusión de la clase

La sesión cerró con la asignación del cuestionario escrito, el videotutorial de GitHub y la página en Confluence. Se pidió revisar las fechas y horas en la plataforma y llevar dudas a la siguiente clase. El profesor conectó el análisis y la documentación con el trabajo posterior del curso.

### 6️⃣ ✅ Síntesis final

Analizar antes de prometer o construir una solución.
No asumir: revisar, comprender, corroborar, evidenciar y validar.
Entender las herramientas y poder explicar el propio trabajo.
Las ramas permiten desarrollar cambios sin alterar de inmediato otras líneas de trabajo.
