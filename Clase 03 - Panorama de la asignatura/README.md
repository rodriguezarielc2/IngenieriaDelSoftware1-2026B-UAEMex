# Clase 03 — Panorama de la asignatura

### 1️⃣ 📘 Identificación

- **Tema principal:** panorama de las unidades del curso y fundamentos para analizar y desarrollar sistemas de software.
- **Subtemas y actividades:** metodologías y ciclo de vida del software; iteraciones y cambios de requisitos; recopilación de información; requisitos funcionales y no funcionales; contexto y límites del sistema; modelo determinista; pruebas; pseudocódigo; actividad breve en línea.
- **Propósito:** conectar los conceptos generales de sistemas con el proceso de análisis, documentación y construcción de una solución de software.

### 2️⃣ 📝 Resumen explicativo

**Ruta de la materia.** El profesor retomó el temario y explicó cómo las unidades avanzan desde la teoría general de sistemas y los modelos de proceso hasta la identificación y análisis de requisitos. En etapas posteriores se documentarán los datos y componentes mediante diagramas y un portafolio de evidencias.

**Ciclo de desarrollo e iteración.** Se presentó el ciclo de vida del software (SDLC) como una secuencia de análisis, diseño, implementación, pruebas, despliegue y mantenimiento. El trabajo puede volver a etapas anteriores cuando cambian los requisitos. El profesor usó el ejemplo de una serie de Fibonacci a la que después se le solicita calcular factoriales y estar disponible como aplicación móvil y web: cada cambio puede afectar diseño, implementación, pruebas, tiempo y recursos. Por ello, se deben prever impactos, entregar incrementos y documentar las decisiones.

**Requisitos y contexto.** Para identificar necesidades se recopila información mediante investigación, observación y entrevistas. Hay que preguntar quién usará el sistema, qué problema atenderá, qué datos manejará y qué resultado se espera. Se distinguieron requisitos funcionales —las funciones que el sistema debe realizar— y no funcionales —condiciones de calidad o servicio, como disponibilidad—. También se mencionó analizar el tratamiento, almacenamiento y protección de los datos. Los diagramas UML, de flujo, secuencia, clases y componentes ayudan a representar la solución y las relaciones entre sus partes.

**Modelos, pruebas y pseudocódigo.** Se revisó el modelo determinista como una forma de obtener resultados esperados a partir de entradas y reglas definidas. Para probar una operación se proponen valores y se compara la salida real con la esperada. El profesor contrastó este caso controlado con situaciones del mundo real, donde incidentes externos y requisitos que cambian pueden alterar el resultado. En la actividad en línea se preguntó qué información se necesita para elaborar pseudocódigo: problema y propósito, entradas, procesos, salidas, variables, constantes, tipos, condiciones, restricciones y operadores. Se explicó el esquema entrada–proceso–salida y su relación con los elementos conectados de un sistema.

**Teoría general de sistemas.** La clase volvió al concepto de sistema como elementos interconectados que operan de manera ordenada para alcanzar un objetivo. El contexto delimita el problema, explica la función de sus entradas y salidas y orienta qué partes conviene analizar. El ejemplo de una computadora mostró cómo descomponer un conjunto en componentes y subcomponentes sin perder de vista su propósito y el uso que dará el usuario.

### 3️⃣ 🧩 Conceptos teóricos y técnicos relevantes

- **SDLC:** ciclo de vida del software, presentado con las etapas de análisis, diseño, implementación, pruebas, despliegue y mantenimiento.
- **Iteración e incremento:** repetición de etapas y entrega progresiva de versiones, incorporando cambios de requisitos con análisis de impacto.
- **Requisito funcional:** función o comportamiento que el sistema debe ofrecer.
- **Requisito no funcional:** condición de calidad u operación, como disponibilidad, rendimiento o resiliencia.
- **Modelo determinista:** modelo que aplica reglas definidas a entradas conocidas para producir una salida esperada.
- **Prueba:** comparación entre el resultado esperado y el resultado obtenido para ciertos datos de entrada.
- **Pseudocódigo:** descripción de un procedimiento mediante pasos, datos, operaciones y condiciones antes de implementarlo en un lenguaje.
- **Contexto del sistema:** entorno y límites que permiten entender el propósito, los usuarios, las dependencias y las condiciones del problema.
- **Descomposición:** análisis de un sistema por componentes y subcomponentes, manteniendo claras sus relaciones y responsabilidades.

### 4️⃣ ⚠️ Problemas, errores o aclaraciones del profesor

- Se aclaró que los paradigmas de programación (por ejemplo, lógico u orientado a objetos) no eran el tema central; la unidad trataría metodologías y organización del desarrollo.
- El profesor revisó el conteo de fases del SDLC y corrigió la lista a seis: análisis, diseño, implementación, pruebas, despliegue y mantenimiento.
- Una solicitud como “agregar un mensaje” o cambiar un color no define por sí sola todos los requisitos; hay que precisar propósito, usuario, comportamiento y posibles impactos.
- Un resultado correcto para un caso matemático simple no demuestra que el sistema cubra las variaciones y restricciones del proceso real.
- Durante la demostración del cuestionario, el profesor indicó que su vista de respuestas no se actualizó como esperaba; continuó la explicación con la actividad.

### 5️⃣ 🧠 Conclusión de la clase

La sesión conectó el análisis de sistemas con las metodologías de desarrollo, los requisitos, las pruebas y la documentación. El contexto y la comprensión del problema orientan qué componentes construir y cómo verificar que la solución atienda las necesidades reales. Se anunció una investigación breve para la siguiente clase.

### 6️⃣ ✅ Síntesis final

El ciclo de software organiza análisis, diseño, implementación, pruebas, despliegue y mantenimiento.
Los cambios de requisitos pueden afectar varias etapas y requieren revisar su impacto.
Los requisitos describen funciones y condiciones de calidad del sistema.
Un modelo de entrada, proceso y salida necesita un problema y un propósito definidos.
El contexto delimita qué analizar y qué resultado debe considerarse correcto.
