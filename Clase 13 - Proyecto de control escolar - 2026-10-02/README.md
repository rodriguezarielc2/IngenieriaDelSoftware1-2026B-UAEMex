# Clase 13 — Proyecto de control escolar

### 1️⃣ 📘 Identificación

- **Tema principal:** organización y alcance del proyecto colaborativo para analizar un sistema de control escolar.
- **Subtemas y actividades:** división por módulos; integración entre equipos; requisitos y modelos de datos; GitHub, Markdown y control de versiones; evaluación individual; planificación y propuesta de mejoras.
- **Propósito:** definir cómo se construirá una documentación común del sistema y cómo se evaluará la comprensión individual del proyecto.

### 2️⃣ 📝 Resumen explicativo

**Módulos y equipos.** El proyecto será compartido por varios equipos, cada uno responsable de un módulo: alumnos, inscripciones, profesores, asignaturas y materias, calendario de exámenes, y registro de calificaciones. Aunque cada equipo trabaje en una parte, el resultado debe ser un sistema integrado. Los módulos intercambian datos y servicios; por eso cada integrante debe conocer el propósito general y explicar cómo se relaciona su módulo con los demás.

**Evaluación individual y colaboración.** El profesor indicó que revisaría las contribuciones en GitHub (por ejemplo, cambios registrados) y también preguntaría a cada estudiante sobre módulos que no desarrolló directamente. Los equipos deben acordar cómo trabajar en el mismo repositorio: commits, ramas, merges y coordinación para evitar sobrescribir el trabajo de otras personas. La evaluación busca comprobar que cada integrante entiende el proyecto, no solo que entregó un fragmento.

**Documento y análisis.** El entregable se preparará en Markdown dentro de GitHub, no en Word. Su estructura incluirá introducción, objetivo, requisitos funcionales y no funcionales, módulos, datos de entrada y salida, interacciones y mejoras propuestas. El análisis parte del modelo de sistemas (entradas, procesos, salidas y contexto) y de preguntas que permitan precisar necesidades. Se mencionó usar una base de datos relacional como parte del sistema de control escolar.

**Calidad de las propuestas.** El profesor pidió no limitarse a copiar definiciones o respuestas de una guía o IA: cada integrante debe revisarlas, entenderlas y justificarlas. La palabra “ineficiente” no identifica por sí sola una falla; debe precisarse. Se puso como ejemplo verificar si la interfaz del sistema es adaptable a dispositivos móviles y pantallas de distintos tamaños (diseño responsivo).

**Planificación.** Se anticipó organizar el trabajo mediante fases y tiempos —análisis, diseño, construcción, pruebas y despliegue— y representar entregas con sprints o un diagrama de Gantt. La clase se centraría principalmente en análisis y diseño, con propuestas documentadas para el desarrollo posterior.

### 3️⃣ 🧩 Conceptos teóricos y técnicos relevantes

- **Módulo:** parte del sistema con responsabilidades específicas que debe integrarse con otros módulos.
- **Requisito funcional:** acción o servicio que el sistema debe ofrecer.
- **Requisito no funcional:** condición de operación o calidad, como facilidad de uso o compatibilidad.
- **Modelo de datos relacional:** organización de entidades y relaciones en tablas vinculadas.
- **Markdown:** formato de texto para documentar títulos, listas, enlaces, tablas y otros elementos.
- **GitHub y Git:** herramientas para alojar cambios, revisar contribuciones y coordinar trabajo compartido.
- **Commit:** registro de un conjunto de cambios en el control de versiones.
- **Merge:** integración de cambios de distintas ramas o líneas de trabajo.
- **Diseño responsivo:** adaptación de la interfaz a distintos tamaños de pantalla y dispositivos.
- **Diagrama de Gantt y sprint:** herramientas para visualizar actividades, duración y entregas planeadas.

### 4️⃣ ⚠️ Problemas, errores o aclaraciones del profesor

- Se advirtió que Git puede reflejar problemas de coordinación: cambios simultáneos sin acuerdos pueden sobrescribir o dificultar integrar el trabajo de otros equipos.
- La división por módulos no elimina las dependencias. Por ejemplo, calificaciones e inscripciones necesitan información de alumnos, profesores, materias y periodos.
- “Ineficiente” debe convertirse en una observación o necesidad concreta antes de proponer una solución; una posible mejora como diseño responsivo debe verificarse en el sistema real.
- El proyecto debe quedar explicado en común: responder solo sobre el módulo propio no demuestra comprensión del sistema completo.
- La guía o la IA pueden aportar ideas, pero el equipo debe validarlas y poder defenderlas.

### 5️⃣ 🧠 Conclusión de la clase

El proyecto de control escolar se abordará como un sistema integrado compuesto por módulos relacionados. La documentación en Markdown, el control de versiones y la comunicación entre equipos servirán para coordinar el trabajo. Cada integrante deberá justificar requisitos y decisiones del sistema completo en una evaluación individual.

### 6️⃣ ✅ Síntesis final

El proyecto se divide en seis módulos que deben integrarse.
Cada estudiante debe comprender el sistema completo, no solo su módulo.
El entregable se documenta en Markdown y se coordina mediante GitHub.
Las propuestas parten de requisitos claros, datos y relaciones entre módulos.
Las mejoras deben justificarse con observaciones verificables del sistema.
